## 目的

macOS には Windows のように「タスクバーの分だけ作業領域を予約する」公開 API がなく、最大化やドラッグで
ウィンドウがタスクバーの下に潜り込む。タスクバーと重なったウィンドウを、AX で移動・リサイズして避けさせる。

## 現状の挙動

- タスクバーは floating レベルの枠なしウィンドウで、他のウィンドウの上に重なって表示される。
  重なられた側のウィンドウ下端（bottom レイアウト）や右端（right レイアウト）のボタン・スクロールバーが隠れる
- タスクバーの矩形は `display_manager::taskbar_bounds(work_area, layout)`（純関数）で決まる。
  bottom は高さ 60px、left/right は幅 210px
- AX によるウィンドウ操作の土台は `window_actions.rs` にある（AXUIElement の特定・属性の書き込み・
  CGWindowID との対応付け `_AXUIElementGetWindow`・メッセージタイムアウト）

## 参考実装（Electron 版）から引き継ぐもの・引き継がないもの

| 項目 | 参考実装 | 本 Plan での扱い |
|---|---|---|
| 重なり判定 | 矩形の交差判定（`isOverlapping`） | 引き継ぐ（純関数・単体テスト） |
| 調整の方向 | bottom → 高さを縮める／right → 幅を縮める／left → 右へずらして幅を縮める（最小幅 100px） | **移動を優先する形に変える**（設計判断 6）。top 方向の調整は不要（タスクバーは上に来ない） |
| ウィンドウ操作 | AppleScript（System Events）でウィンドウ名の部分一致 | **AX 直接**に置き換える。名前一致は誤爆し、名前を AppleScript に埋め込むためインジェクションの余地もあった |
| タスクバーの大きさ | 210 / 60 を関数内に直書き | `taskbar_bounds` を共用する |
| 起動のきっかけ | IPC `adjustOverlappingWindows` の受け口だけで、呼ぶ側がなかった | AX 通知で自動起動する（下の設計判断 1） |

## 設計判断（2026-10-24 オーナー回答で確定）

1. **いつ調整するか**: ウィンドウの生成時（AXWindowCreated）と、移動・リサイズが落ち着いたとき
   （AXMoved / AXResized を 500ms デバウンス）に自動で調整する
2. **ユーザーが意図的に重ねたときの扱い**: 大幅に突き抜けて置いたときは調整しない。ちょっと重なる程度なら調整する
   - 判定（エージェントの具体化。違和感があれば閾値を見直す）: タスクバー側にある**ウィンドウの外側の辺が、画面の端を越えている**
     （bottom なら下端がディスプレイ下端より下、right なら右端がディスプレイ右端より右）ときは「突き抜け」＝意図的とみなし、調整しない。
     外側の辺がタスクバーの帯の中（画面内）に収まっている重なりは調整する
   - 判定の境界には数 px の許容幅を持たせる（端にぴったり合わせたウィンドウを誤判定しないため）
   - この判定で綱引きは起きにくいが、調整による自己通知を無視するクールダウンは別途必要（フェーズ 3）
3. **既定値**: **有効**。設定画面でオフにできる
4. **対象外にするウィンドウ**
   - フルスクリーン（AXFullScreen）: 既定では触らない。設定項目「フルスクリーンを解除して避ける」（**既定無効**）を設け、
     有効なら AXFullScreen を false にしてから通常の調整を行う
   - 最小化中、layer が 0 以外（パネル・オーバーレイ）、既存のフィルタ（labeledFilters）で除外されているウィンドウ
   - サイズを変えられないウィンドウ（AXSize が設定不可）は移動だけを試み、移動で避けられなければ触らない
5. **縮めすぎの下限**: 縮めた結果が幅・高さ 200px 未満になるなら調整しない（6 のルールで移動が優先されるため、まず起きない想定）
6. **調整の方向**: ウィンドウの大きさに余裕があれば**移動を優先**し、足りなければ縮める
   - 使える領域 = ディスプレイの作業領域（メニューバー・Dock を除いた範囲）からタスクバーの帯を除いた範囲
   - その方向の大きさが使える領域に収まるなら、タスクバーの内側の辺にそろうまで移動する（大きさは変えない）
     - bottom: 下端をタスクバーの上端にそろえる / right: 右端をタスクバーの左端にそろえる / left: 左端をタスクバーの右端にそろえる
   - 収まらないなら、使える領域の端に寄せたうえで、はみ出す分だけ縮める（= 使える領域いっぱいにする）

## 変更内容（フェーズ）

### フェーズ 1: 判定と調整量の計算（純関数・単体テストで完結）

- **対象**: 新規 `src-tauri/src/overlap.rs`
- `adjustment(window: Rect, taskbar: Rect, display: Rect, work_area: Rect, layout, min_size) -> Option<Rect>` を実装する
  （設計判断 2 の突き抜け判定・6 の移動優先・5 の下限をすべてここに入れる）
- 参考実装のテスト（144 行）の観点（重ならない／各レイアウトでの調整／下限）を Rust に移植し、
  「余裕があれば移動だけ」「足りなければ縮める」「突き抜けは触らない」「境界の許容幅」のケースを足す
- マルチディスプレイ: ウィンドウの中心が属するディスプレイのタスクバーとだけ比べる

### フェーズ 2: AX による移動・リサイズ

- **対象**: `window_actions.rs` に `set_frame(pid, window_number, rect)` を追加
- CGWindowID → AXUIElement の特定は既存の `find_ax_window` を流用する（名前一致は使わない）
- AXPosition / AXSize を `AXValue`（CGPoint / CGSize）で書き込む。書き込み可否は `AXUIElementIsAttributeSettable` で確認する
- spawn_blocking ＋タイムアウト、メッセージタイムアウト 1 秒（既存方針どおり）
- 信頼境界: 調整対象はサーバー側（CGWindowList）で取得したウィンドウだけにし、フロントから座標を受け取らない
  （Feedback 2026-07-14 の改善アクション）

### フェーズ 3: きっかけの配線と設定

- **対象**: `ax_observer.rs`（AXMoved / AXResized の購読追加）、`window_observer.rs`、`store.rs` / `types.ts`（設定項目）、設定画面
- 設計判断 1 に沿って配線する。調整そのものが AXMoved / AXResized を発火させるため、
  自分の調整による通知を無視する仕組み（調整直後のクールダウン）を必ず入れる
- 設定 `autoAvoidTaskbarOverlap`（既定 **true**）と `exitFullScreenToAvoidTaskbar`（既定 false）を
  store.rs と types.ts に同時に追加し、設定画面にトグルを置く
- 既定 true の項目を既存ユーザーの設定に足すため、ストアの読み込みで欠けたキーが既定値で補われることを確認する

### フェーズ 4: 実機検証

`bun run dev` ＋ `TASKBAR_DEBUG_LOG=1` で、ax-title-observer と同じ osascript プローブにより検証する
（手順は knowhow/macos-axobserver-runloop-thread.md）。

- bottom / right / left の各レイアウトで、少し重なったウィンドウが移動で避ける（大きさは変わらない）
- 使える領域より大きいウィンドウは、領域いっぱいに縮む
- 画面の端を越えて突き抜けたウィンドウには触らない
- 緑ボタンの拡大（zoom）・ダブルクリック拡大で避ける
- 調整と通知の無限ループが起きない（ログで調整回数を数える）
- フルスクリーンには触らない。「フルスクリーンを解除して避ける」を有効にすると解除して避ける
- サイズ固定のウィンドウは移動だけで避け、避けられなければ触らない
- 設定オフでは一切動かない

## 実装メモと検証結果（2026-10-24）

**実装**:
- `overlap.rs`（新規）: 純関数 `adjustment` と、AX 通知を受けて全ウィンドウを判定・調整するループ。
  500ms 静穏で判定し、**1.5 秒後にもう一度判定する**（フルスクリーン化などのアニメーションは通知の時点で途中で、
  終了後に通知が来ないことが実機で分かったため）
- 同じウィンドウの調整は **30 秒間に 3 回まで**（従わないアプリとの綱引きを打ち切る。ユーザーが 4 回重ね直したら
  意図的とみなして手を引くことにもなる）。当初は「3 秒間再調整しない」だったが、レビューで「調整直後に重ね直すと放置される」
  「綱引きが低頻度で永続する」と指摘され置き換えた
- **マウスボタンが押されている間は判定を保留**し、300ms ごとにやり直す（ドラッグ中にマウスを 0.5 秒止めただけで、
  掴んでいるウィンドウを動かさないため。レビュー指摘）。この挙動は実機の自動操作では再現できず、コードと単体テストの範囲で確認した
- `window_actions::set_frame`: CGWindowID 一致だけで対象を特定（タイトル一致は使わない）。縮めてから動かす
- `ax_observer.rs`: AXWindowMoved / AXWindowResized を追加。移動・リサイズは重なり回避だけに、生成は両方に送る
  （ドラッグ中の連発で 'process' を再取得しないため）
- タスクバーの矩形は計算式ではなく実際のタスクバーウィンドウの位置から取る。作業領域・ディスプレイは Tauri の Monitor を論理 px に変換
- 設定 `autoAvoidTaskbarOverlap`（既定 true）/ `exitFullScreenToAvoidTaskbar`（既定 false）。
  store.rs は `serde(default)` で、キーの無い既存設定を読んでも他の設定が既定値に戻らない（テスト追加）

**実機検証（`TASKBAR_DEBUG_LOG=1 bun run dev`、TextEdit を System Events で配置）**:

| レイアウト | 少し重なる | 突き抜け | 使える領域より大きい |
|---|---|---|---|
| bottom | 800×600 の下端 1400 → 上へ 20pt 移動（大きさそのまま） | 下端 1600 → 触らない | 高さ 1410 → 1350 に縮小 |
| right | 右端 3300 → 左へ 70pt 移動 | 右端 3700 → 触らない | 幅 3440 → 3230 に縮小 |
| left | 左端 100 → 右へ 110pt 移動 | 左端 -300 → 触らない | x=210・幅 3230 に寄せて縮小 |

- サイズ固定（電卓、AXSize 設定不可）: 移動だけで避けた
- フルスクリーン: 既定では触らない。「解除して避ける」をオンにすると、再判定のタイミングで解除され元の位置に戻った
- 設定オフ: 重ねても動かない（ログ `disabled by option`）
- 調整後に同じウィンドウが再調整されるループは起きなかった（各ケースで adjusted は 1 回）
- 回数制限: 3 秒以内に同じウィンドウを 4 回重ね直すと、3 回目までは避け、4 回目は `gave up` で触らなかった
- 既知の制約（レビュー Medium・許容）: 調整が生む AXWindowMoved により、空振りの判定サイクルが 1 回余分に走る。
  CGWindowList の取得 2 回分で、待機時の負荷にはならない
- 既知の制約（レビュー Low・許容）: アプリがサイズを丸めた場合に実サイズを読み戻さないため、わずかに重なりが残ることがある。
  次の通知で再判定される
- 注意: 判定は通知のたびに全ウィンドウに対して行うため、レイアウトを変えたあとの最初の通知で、
  新しい位置のタスクバーに重なっている既存のウィンドウもまとめて避ける（検証中に right/left へ切り替えた際、
  オーナーのウィンドウ 8 枚が動いた。7 枚は元の位置に戻した）
